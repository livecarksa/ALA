# معمارية وصلة — النموذج الأولي للنواة

مرجعية هذه الوثيقة: القسمان 4.1 و4.2 من دراسة الجدوى (يونيو 2026).

## 1. الوحدات الثلاث في الدراسة وما يغطيه هذا النموذج

| الوحدة في الدراسة | حالتها هنا |
|---|---|
| نواة المحفظة والتسوية (تكامل بنكك + المحول القومي + دفتر مزدوج القيد) | ممثلة بمحاكٍ في الذاكرة: `settlement/engine.py` + `settlement/ledger.py` |
| محرك التوكنات الأوف لاين (مفاتيح، توقيع، سلسلة، صلاحية) | **مكتملة كخوارزمية**: `token_engine/` |
| طبقات النقل (BLE / QR / SMS مضغوط) | غير ممثلة — التوكن ينتقل كبنية بيانات مباشرة |

## 2. دورة حياة التوكن

```
تسوية سابقة ─► مرساة سلسلة (anchor) لكل جهاز
                    │
   [أوف لاين] sender.send() ─► توكن موقّع Ed25519
                    │   prev_hash = رأس السلسلة، seq متسلسل
                    │   ينتقل عبر BLE/QR/SMS (خارج النطاق هنا)
                    ▼
        recipient.receive() ─► تحقق محلي فوري (توقيع، صلاحية، وجهة)
                    │
   [عودة الشبكة] الطرفان يرفعان توكناتهما
                    ▼
        SettlementEngine.settle_batch()
                    │  يعيد كل الفحوص + يمشي السلسلة من المرساة
                    │  تفرع؟ ─► الفرع الأسبق يُسوّى، الآخر يُرفض، الحساب يُجمَّد
                    ▼
        قيد مزدوج في الدفتر + مرساة جديدة لكل جهاز
```

## 3. نموذج التهديد وكيف يُصد كل هجوم

| الهجوم | الصد | الاختبار |
|---|---|---|
| إنفاق مزدوج بتفريع السلسلة في دفعة واحدة | توكنان يشيران لنفس `prev_hash` → كشف حتمي، تسوية الأسبق فقط، تجميد الحساب | `test_double_spend.py::TestForkDetection` |
| **تفرع يصل عبر دفعتين منفصلتين** (مستلمان يتصلان في أوقات مختلفة) | فهرس دائم `(sender, prev_hash)→token_id` لكل نقطة استُهلكت؛ أي إنفاق ثانٍ منها = `DOUBLE_SPEND` وتجميد، حتى بعد إعادة تشغيل البوابة | `TestForkDetection::test_fork_across_separate_batches_detected`، `test_gateway.py::test_double_spend_freeze_survives_restart` |
| إعادة رفع توكن مسوّى (replay) | فهرس `token_id` المسوّاة (دائم) — تسوية واحدة مهما تكرر الرفع | `TestReplayAndDuplicates` |
| تطبيق معدَّل يتجاوز سقف المحفظة | المحرك يعيد فحص السقف اليومي، ويصمد العدّاد عبر الدفعات والديمومة | `test_daily_cap.py::TestEngineSideCap`، `test_review_hardening.py::TestCapPersistsAcrossBatches` |
| **تقسيم السقف بطابع إصدار مستقبلي** | رفض `issued_at > now + هامش` (`FUTURE_DATED`) وفرض حد العمر خادمياً (`BAD_TTL`) | `test_review_hardening.py::TestFutureDatingCapAttack` |
| سلسلة مفبركة تنفق فوق الرصيد | فحص الرصيد المسوّى عند كل توكن، وما بُني فوق المرفوض لا يُسوّى (`SUPERSEDED`) | `TestCraftedChains`، `TestSupersededDescendants` |
| **تعطيل أموال الضحية بتدوير مرساتها** | المرساة لا تتقدم إلا بتوكن سُوّي فعلاً — رفع توكن لا يُسوّى لا يحرّكها | `TestAnchorGriefing` |
| تعديل المبلغ/المستلم بعد التوقيع | توقيع Ed25519 على الحمولة القانونية كاملة | `test_expiry_and_tamper.py::TestTamper` |
| التباس نوعي (`amount=True`) أو عملة غير قياسية | رفض `bool` صراحةً وفرض عملة 3 حروف لاتينية كبيرة | `TestTypeConfusion` |
| انتحال هوية مرسل | `device_id` مشتق من المفتاح العام (sha256) — لا انتحال دون المفتاح الخاص | `TestTamper` |
| اكتناز توكنات وتسويتها بعد شهور | انتهاء صلاحية 72 ساعة؛ المنتهي لا يُسوّى وقيمته تعود للمرسل | `TestExpiry` |
| جهاز مسروق بمفتاح قديم | تدوير المفتاح في السجل → `KEY_MISMATCH` | `test_double_spend.py` |

**خسارة الحد الأقصى لأي اختراق فردي = السقف اليومي** — هذه هي الضمانة الاقتصادية التي تجعل النظام قابلاً للترخيص (النمط نفسه في UPI Lite X وتجارب CBDC الأوف لاين).

### مصادقة طلبات البوابة (`gateway/auth.py`)

كل طلب (عدا التسجيل — بوابة الانضمام المفتوحة) موقّع بمفتاح الجهاز Ed25519
على `الفعل + المسار + الطابع الزمني + بصمة الجسم`. الخادم يتحقق ضد المفتاح
العام المسجَّل (إثبات حيازة)، فلا يستطيع أي طرف على الشبكة رفع دفعة أو تمويل
حساب أو قراءة رصيد نيابة عن غيره. نافذة زمنية (±5 دقائق) تصدّ إعادة الإرسال،
والتسوية idempotent بمعرّف الدفعة والإيداع بمرجعه فلا أثر مزدوج داخل النافذة.
الاختبارات في `test_auth.py`.

### حدود معروفة (موثقة من مراجعة مجلس الخبراء)

- **حد العمر يقيّد تضخيم السقف لا يلغيه**: المحرك يرفض التواريخ المستقبلية ويفرض عمراً أقصى 72 ساعة، فيبقى للمهاجم تأريخ خلفي داخل نافذة العمر — أي مضاعفة السقف بحد أقصى يقارب عدد أيام النافذة (3–4). الإغلاق الكامل يتطلب سقفاً متدحرجاً على النافذة أو طابعاً زمنياً موقّعاً من الخادم، وهو بند إنتاجي. (إجمالي الخسارة محدود أصلاً برصيد الجهاز المموَّل.)
- **تقرير المطابقة مفتوح**: `/api/v1/reconciliation` تشغيلي بلا مصادقة في النموذج؛ الإنتاج يقصره على دور المشغّل.
- **مفاتيح في الذاكرة/الملف**: الطبقة الرابعة (البيئة الآمنة للجهاز) خارج النموذج الأولي.
- **بوابة محاكية**: تمثّل واجهات بنكك ولا تتصل بها فعلياً (بند اتفاقية الوصول التقني).

## 4. قرارات تصميم مقصودة

- **المستلَم غير قابل للإنفاق قبل التسوية**: التوكنات المستلمة تُخزن وتُرفع، ولا تتحول رصيداً أوف لاين إلا بعد تسويتها. يمنع بناء سلاسل قيمة متعددة القفزات يستحيل التحقق منها أوف لاين (نمط UPI Lite X).
- **سياسة التفرع: الأسبق يُسوّى**: حماية المستلم البريء الأول؛ الخسارة تقع على المحتال (تجميد) لا على من قبل التوكن بحسن نية.
- **التوكن المنتهي لا يكسر السلسلة**: يُرفض هو وحده وتُكمل التسوية ما بعده، لأن السلسلة متصلة بنيوياً وإن سقطت قيمة حلقة منها.
- **مبالغ صحيحة بالقرش**: لا float في مسار المال إطلاقاً.
- **المرساة تتجدد بعد كل تسوية**: أي توكن قديم خارج السلاسل المسوّاة يصبح `CHAIN_BROKEN` تلقائياً.

## 5. خارطة ما بعد النموذج الأولي (مرتبطة ببوابات الدراسة)

1. **بوابة 2 (نموذج عامل)**: ربط محرك التسوية بواجهات بيئة اختبار بنكك بدل الذاكرة، وقاعدة بيانات معمّرة بمعاملات idempotent.
2. مفاتيح داخل Secure Enclave / Android StrongBox (الطبقة الرابعة).
3. طبقات النقل: BLE وQR للهواتف الذكية، وترميز SMS مضغوط (CBOR + Base45) للهواتف العادية.
4. KYC متدرج ومراقبة أنماط مشبوهة داخل النواة (القسم 7.2).
5. مراجعة أمنية مستقلة قبل تجربة التسعين يوماً (سجل المخاطر، القسم 8).
