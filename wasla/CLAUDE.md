# خطة Claude Code — إكمال بناء «وصلة» (نسخة بنكك)

> **كيفية الاستخدام:** انسخ هذا الملف باسم `CLAUDE.md` في جذر المشروع. Claude Code سيقرؤه تلقائياً في كل جلسة ويلتزم به. عند أي قرار معماري جديد، حدّث قسم «سجل القرارات» في نهاية الملف.

---

## 1. هوية المشروع والقرار الحاكم

«وصلة» تقنية تحويل مالي **أوف لاين حقيقي** تعمل داخل تطبيق بنكك (بنك الخرطوم): المال ينتقل من جهاز إلى جهاز عند الانقطاع الكلي لشبكة الاتصالات (لا عند غياب الإنترنت فقط)، عبر توكنات موقّعة Ed25519 بسقف يومي وسلسلة توقيعات متتابعة تكشف الإنفاق المزدوج، ثم تُسوّى فور عودة الاتصال.

**القرارات الحاكمة — لا تُناقش في الكود، تُنفَّذ:**

| القرار | المعنى التنفيذي |
|---|---|
| بنكك فقط | لا كود لممرات شتات، لا أطراف إرسال خارجية، لا تكامل مع بنوك أخرى. طرف واحد: بنك الخرطوم |
| تسوية داخل البنك | التحويل من محفظة عميل بنكك إلى محفظة عميل بنكك. **لا اعتماد على المحوّل القومي (EBS/العسجد) في أي مسار حرج للمرحلة الأولى** |
| الأوف لاين هو البطل | كل أولوية للتحويل الأوف لاين. بوابة الدفع الإلكتروني وأجهزة POS مراحل لاحقة — لا تُبنى الآن ولا تُستبق ببنية تحتية مبكرة |
| المحرك سرّ تجاري | `wasla_core` لا يُنشر ولا يُرفع لأي مستودع عام ولا تُوثَّق خوارزمياته في أي ملف يخرج من الفريق. لا براءة الآن |
| نموذج العمل | تجربة مفهوم مدفوعة (PoC) داخل بنكك ← ترخيص بنسبة من المعاملات. الكود يُبنى بحيث يسهل تسليم PoC محدود النطاق |

## 2. المعمارية والحزم

```
wasla/
├── packages/
│   └── wasla_core/          # المحرك — Dart نقي بلا Flutter، سرّ تجاري
│       ├── lib/src/
│       │   ├── identity.dart      # توليد المفاتيح Ed25519 وتخزينها
│       │   ├── reservation.dart   # الحجز المسبق والسقف اليومي
│       │   ├── token.dart         # بنية التوكن والتوقيع والتسلسل
│       │   ├── chain.dart         # بناء السلسلة وكشف التفرع
│       │   ├── codec.dart         # CBOR + Base45 للترميز المضغوط
│       │   └── verify.dart        # تحقق المستقبِل أوف لاين
│       └── test/                  # تغطية ≥ 90% — بوابة إلزامية
├── app/                     # تطبيق Flutter (واجهة PoC داخل نمط بنكك)
│   ├── lib/features/
│   │   ├── wallet/          # المحفظة والحجز
│   │   ├── send/            # الإرسال: QR ثم BLE ثم SMS
│   │   ├── receive/         # الاستقبال والتحقق أوف لاين
│   │   ├── history/         # السجل والمطابقة
│   │   └── settle/          # مزامنة التسوية عند عودة الاتصال
│   └── integration_test/    # سيناريو الديمو الستّي كاختبار قبول
└── supabase/
    ├── migrations/          # reservations, settled_tokens, conflicts + RLS
    └── functions/settle/    # تحقق السلسلة + settle_accept الذرّية
```

**المكدس:** Flutter + Riverpod، `cryptography` للتوقيع، `flutter_secure_storage` للمفاتيح (المفتاح الخاص لا يلمس App State ولا SharedPreferences أبداً)، `qr_flutter` + `mobile_scanner`، Supabase (Postgres + Edge Functions/Deno WebCrypto). العربية أولاً: كل الواجهات RTL، `intl` مع `ar` افتراضياً، أرقام غربية في المبالغ.

## 3. مراحل البناء (بالترتيب — لا تقفز مرحلة)

### المرحلة A — تصلّب المحرك (الأسبوعان 1–2)
اكتمل برهان المفهوم؛ المطلوب تحويله محركاً موثوقاً: استخراج كل منطق التوكن من الديمو إلى `wasla_core` نقياً بلا اعتماد على Flutter، تغطية اختبارات ≥ 90% تشمل صراحة: قبول سلسلة سليمة، رفض سلسلة متفرعة (إنفاق مزدوج)، رفض توكن منتهي الصلاحية (72 ساعة)، رفض تجاوز السقف اليومي، رفض توقيع تالف، ثبات الترميز ذهاباً وإياباً (CBOR/Base45). أي فشل اختبار يمنع الدمج.

### المرحلة B — التسوية الحقيقية (الأسابيع 3–5)
دالة `settle` الطرفية: تحقق التوقيع والتسلسل والصلاحية والسقف، تسجيل التفرع في `conflicts` ورفضه، تحديث الأرصدة عبر دالة SQL ذرّية `settle_accept` (معاملة واحدة: إدراج في `settled_tokens` + تحديث الرصيد + إغلاق الحجز — تنجح كلها أو لا شيء). حالات الفشل أولوية قصوى: انقطاع أثناء التسوية يجب ألا يفقد أو يكرّر معاملة (idempotency عبر معرّف التوكن). شاشة مطابقة تثبت: المحجوز − المسوّى − المنتهي = صفر.

### المرحلة C — قناة SMS للهواتف العادية (الأسابيع 6–8)
الترميز المضغوط للتوكن في حمولة SMS (قد يتطلب تقسيماً متسلسلاً)، أمر USSD-مُشابه للعرض فقط إن لزم، وتدفق استقبال يدوي بإدخال الرمز. هذه بوابة غير المصرفيين — لا تُختصر.

### المرحلة D — واجهة PoC بنمط بنكك (الأسابيع 9–10)
واجهة عربية RTL نظيفة تحاكي اندماج الخدمة داخل بنكك (شاشة داخل تطبيق البنك لا تطبيق مستقل بهوية منافسة)، تدفقات: حجز ← إرسال ← استقبال ← تسوية ← مطابقة، مع شارة «أوف لاين ✈» الواضحة وسيناريو الديمو الستّي قابلاً للتشغيل أمام لجنة البنك في أي لحظة.

### المرحلة E — بوابات الجودة قبل أي تجربة حية
اختبار قبول آلي يطابق سيناريو الديمو الستّي يعمل مع كل بناء، فحص ثابت (`flutter analyze` بلا تحذيرات)، مراجعة أمنية مستقلة **قبل** أي مال حقيقي — بند غير قابل للتفاوض، وخطة استرداد مفاتيح عند فقد الجهاز (استرداد عبر البنك بهوية العميل، لا نسخ سحابي للمفتاح الخاص).

**خارج النطاق الآن (لا تبنِ لها شيئاً):** بوابة دفع التجارة الإلكترونية، أجهزة POS، تكامل المحوّل القومي، لوحة وكلاء كاملة، أي ممر خارجي.

## 4. ممارسات العمل الإلزامية

**كل جلسة Claude Code تبدأ بـ:** قراءة هذا الملف، ثم `git status` و`flutter test`، ثم العمل على مهمة واحدة محددة تُغلق بـ commit واضح الرسالة (العربية أو الإنجليزية، صيغة: `feat|fix|test|refactor: وصف`). لا جلسة تلمس أكثر من طبقة واحدة (محرك/تسوية/واجهة) إلا للإصلاح العابر.

**الاختبارات قانون:** لا ميزة بلا اختبار يسبقها أو يرافقها. النواة التشفيرية لا تُعدَّل أبداً دون تشغيل كامل حزمة اختباراتها. أي تعديل على بنية التوكن يستلزم ترقية رقم إصدار البروتوكول في الترميز وحالة اختبار توافق خلفي.

**الأسرار:** لا مفاتيح ولا `service_role` في الكود أو الـ commits — كل الأسرار في `.env` (مدرج في `.gitignore`) ومتغيرات بيئة Supabase. المستودع خاص، ولا يُضاف متعاون خارجي دون اتفاقية سرية موقّعة.

**العربية أولاً:** كل نص واجهة يُكتب عربياً في ملفات `intl` من اليوم الأول (لا نصوص صلبة في الكود)، والتخطيط RTL يُختبر بصرياً في كل شاشة جديدة.

## 5. تعريف «جاهز للعرض على البنك»

التجربة تُعد جاهزة حين: سيناريو الديمو الستّي يعمل على جهازين حقيقيين بوضع الطيران الفعلي بنسبة نجاح 100% في عشر إعادات متتالية، والتسوية تكتمل خلال ثوانٍ من عودة الاتصال، والمطابقة صفر فروقات، ومحاولة الإنفاق المزدوج تُرفض وتُسجَّل في `conflicts`، وقناة SMS تنقل توكناً كاملاً بين هاتفين، وكل الاختبارات خضراء.
